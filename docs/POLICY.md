# Scoring and policy (synthetic demonstration)

`POST /api/v1/applications` submits a business application with matching active consent. `POST /api/v1/applications/{id}/score` computes point-in-time features, calibrated champion and challenger default probabilities, a 300–900 score and A–E risk tier, and a **system recommendation only**. A bank officer remains the final decision maker. The response includes rule results, an indicative offer, expected loss, model agreement, and evidence completeness.

The versioned rules in `backend/app/config/policy.yaml` are reloaded on each scoring request. The effective version includes a hash of the policy file, so changing a threshold creates a new recommendation while a retry with the same application, model, and policy version returns the persisted response. Each failed rule has a stable code for adverse-action text. Minimum vintage and excluded sector cause DECLINE. Exposure, DSCR and instalment cap failures can produce a reduced, referred offer. A large champion/challenger disagreement or high risk tier forces REFER. Rate bands are illustrative demo settings, not real lending terms.

The affordability cap is the suggested tenor times the lower of estimated net monthly cash flow divided by the DSCR floor and the permitted share of monthly inflow. Recommended amount is the minimum of requested amount, affordability cap and tier cap. Expected loss is calibrated champion PD × configured LGD × recommended amount. The DSCR uses known debt service only; the source schema does not yet contain existing instalment amounts, so its missing-data warning must be reviewed by an officer.

The integrity hook currently returns `pending` and no flags. Prompt 13 must replace it before fraud-based decisions. The synthetic-data calibration does not establish production confidence; the assurance block reports the test Brier score and labels confidence as limited. `Decision.outcome=reject` is exposed as `DECLINE` in the API because the existing database enum uses `reject`.
